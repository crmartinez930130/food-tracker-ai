# Design

## Context

Greenfield personal project — no existing code. See proposal.md for motivation. Constraints that shape this design: single user, local-only deployment (no cloud, no public ingress), the user's own Anthropic API key paying per call, and a KMP/Compose frontend with Android as the priority target.

## Goals / Non-Goals

**Goals:**
- A working end-to-end slice: photo in, structured nutrition data out, user can correct it, it persists, summaries reflect it.
- Keep the API key server-side only, and keep per-request Claude cost predictable and controllable.
- A schema-versioned local database that survives app iteration without manual migration pain.

**Non-Goals:**
- Auth, multi-user, cloud sync, offline-first conflict resolution — no accounts exist, so none of this applies.
- Exact nutritional accuracy — this is an AI *estimate* the user corrects, not a lab-grade nutrition database.
- iOS build pipeline polish — iOS is a secondary target; commonMain should stay portable, but iOS-specific work (signing, packaging) is out of scope for this change.

## Decisions

### 1. Database: SQLite via Drizzle ORM + better-sqlite3
**Choice:** `drizzle-orm` with the `better-sqlite3` driver, schema in `backend/src/db/schema.ts`, migrations generated by `drizzle-kit` and committed to `backend/src/db/migrations/`.

**Why:** Single file, zero server process, fits "no extra infrastructure." Drizzle gives TypeScript-inferred query types and a migration generator, directly addressing the schema-versioning risk the user flagged — without the code-gen step and heavier runtime of Prisma. `better-sqlite3` is synchronous, which is fine (even desirable — simpler code, no accidental interleaving) for a single-user local server with no concurrent writers.

**Alternatives considered:**
- Raw `better-sqlite3` + hand-written migration files: simpler dependency graph, but you re-invent migration tracking (which files ran, in what order) — not worth it for the marginal simplicity gain.
- Prisma + SQLite: heavier (codegen step, separate schema DSL, larger install) for a single-user local app; Drizzle's plain-TS schema is a better fit.

### 2. Structured output from Claude: `messages.parse()` + Zod schema
**Choice:** Use the Anthropic TypeScript SDK's `client.messages.parse({ output_config: { format: zodOutputFormat(MealAnalysisSchema) } })`, not forced tool-use (`tool_choice`) and not free-text parsing.

**Why:** This is the SDK's current recommended mechanism for guaranteed-shape JSON — it validates the response against the Zod schema for you (`response.parsed_output`) and is simpler than defining a dummy "tool" purely to coerce structure. Free-text parsing (asking Claude to "respond in JSON") is unreliable — models can add prose, use inconsistent key names, or return invalid JSON.

**Schema (`backend/src/services/meal-analysis-schema.ts`):**
```ts
const MealAnalysisSchema = z.object({
  items: z.array(z.object({
    name: z.string(),
    estimatedGrams: z.number(),
    confidence: z.enum(["low", "medium", "high"]),
    calories: z.number(),
    proteinGrams: z.number(),
    fatGrams: z.number(),
    carbsGrams: z.number(),
  })),
  totalCalories: z.number(),
  totalProteinGrams: z.number(),
  totalFatGrams: z.number(),
  totalCarbsGrams: z.number(),
  notes: z.string().optional(),
});
```

**Alternatives considered:**
- Forced tool_choice with a `record_meal_analysis` tool: works, but adds an extra layer (tool definition + tool_result round-trip) for no benefit over `messages.parse()` when there's no actual tool execution happening.

### 3. Model selection: configurable, default `claude-opus-5`
**Choice:** Read the model id from an environment variable (`ANTHROPIC_MODEL`, defaulting to `claude-opus-5`) rather than hardcoding it.

**Why:** Opus-tier gives the best accuracy for visual portion/food estimation, which is the highest-risk part of this product. But this is the user's own metered key — making the model a config value (not a code change) lets them trade accuracy for cost later (e.g. `claude-sonnet-5`) without touching code, once they've seen real per-analysis cost.

### 4. Image preprocessing: backend-side with `sharp`
**Choice:** Before calling Claude, the backend resizes the uploaded image so its longest edge is ≤ ~1568px and re-encodes as JPEG (~80% quality) using `sharp`.

**Why:** Claude's vision token cost scales with image resolution; oversized phone-camera photos (often 3000px+) cost more tokens with no accuracy benefit past a resolution ceiling. Doing this once, backend-side, avoids duplicating image-processing logic across Android and (later) iOS. Verify the exact current resize threshold against Anthropic's vision docs at implementation time (`find-docs`/ctx7), since this changes independently of the SDK API surface covered above.

**Alternatives considered:**
- Client-side compression (KMP): saves upload bandwidth, but home-network bandwidth isn't the bottleneck here, and it means writing/maintaining platform-specific image code on both Android and iOS for the same outcome.

### 5. API key handling
**Choice:** `ANTHROPIC_API_KEY` lives only in `backend/.env` (gitignored, loaded via Node's built-in `--env-file` or `dotenv`). No Claude call is ever made from the KMP app.

**Why:** The backend is the only trust boundary that needs to hold the secret. This falls out of the existing architecture (app talks to backend, backend talks to Claude) rather than requiring extra design — but it's worth stating explicitly as a constraint so it isn't accidentally violated later (e.g., don't add a "direct upload to Claude" fast path from the app).

### 6. REST API shape
```
POST   /api/meals/analyze      multipart image -> MealAnalysis (not persisted)
POST   /api/meals              { analysis, corrections?, occurredAt? } -> persisted MealEntry
GET    /api/meals?date=YYYY-MM-DD
GET    /api/meals/:id
PATCH  /api/meals/:id
DELETE /api/meals/:id
GET    /api/summary/daily?date=YYYY-MM-DD
GET    /api/summary/weekly?startDate=YYYY-MM-DD
```
Analyze and save are separate calls (rather than one "analyze and auto-save" call) because the spec requires the user to review/correct before persisting — collapsing them would force a save-then-edit-then-resave flow instead.

### 7. Monorepo layout
```
food-tracker-ai/
├── backend/    (Node + TS, Express, Drizzle/SQLite)
├── frontend/   (KMP + Compose Multiplatform, composeApp module)
├── openspec/
└── README.md
```
Two top-level dirs, no shared build tooling between them (different ecosystems — npm vs Gradle) — a shared "packages" layer would be premature for a two-module personal project.

## Risks / Trade-offs

- **[Risk]** AI-estimated portion sizes are frequently wrong (camera angle, occlusion, unfamiliar foods) → **Mitigation:** mandatory review/correct step before save (`meal-tracking` requirements), plus a per-item `confidence` field surfaced to the UI.
- **[Risk]** Uncontrolled Claude spend if the app is used heavily or a client bug causes retry storms → **Mitigation:** log `usage.input_tokens`/`output_tokens` per analysis from day one; image preprocessing caps per-request cost; no automatic retries without a backoff in the analyze endpoint.
- **[Risk]** Single SQLite file with no backup — disk failure or accidental delete loses all history → **Mitigation:** out of scope for this change's code, but document a manual backup step (copy the `.sqlite` file) in the README; a scheduled backup task is a reasonable future change, not foundational.
- **[Risk]** Backend host/port must be reachable from the phone on the home network (not just `localhost`) → **Mitigation:** backend binds to `0.0.0.0` and the port is configurable; the app's backend base URL is a build/runtime config value, not hardcoded to `localhost`.
- **[Trade-off]** Choosing Drizzle over raw SQL/better-sqlite3 adds one dependency and a small learning curve in exchange for type safety and migration tracking — judged worth it given the user explicitly flagged schema versioning as a concern.

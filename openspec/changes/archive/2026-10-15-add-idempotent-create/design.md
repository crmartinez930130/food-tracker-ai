# Design

## Context

- The backend is a single Node process on `better-sqlite3`, which is synchronous: two requests never run their database code at the same time, and a `db.transaction(...)` callback runs without interleaving.
- `createMeal` (`src/db/meal-repository.ts`) inserts the `meals` row and then its `meal_items` rows, today without a transaction. `createWaterLog` is a single insert that returns the row as is, so a new column appears in water responses (`POST` and `GET /api/water`) automatically.
- Meal responses are built by `toMealEntry`, so a new field has to be added there and to the `MealEntry` domain type.
- Migrations are generated by `drizzle-kit generate` from `src/db/schema.ts` and applied on startup.
- Request bodies are validated with zod 4 schemas in `src/routes/schemas.ts`; their errors become 400s through `validationErrorFrom`.

## Goals / Non-Goals

**Goals:**
- A retried `POST /api/meals` or `POST /api/water` with the same `clientId` never creates a second entry, even if it arrives while the first is still being processed.
- The retry gets a success response with the stored entry, so the app's queue can mark it as sent.
- Clients that don't send `clientId` see no change in behaviour.

**Non-Goals:**
- Idempotency for edits, deletes, favorites, goals or weight.
- Detecting that a retry carries different data than the original (the client never changes a queued entry).
- Sending `clientId` from the app (#70).

## Decisions

1. **The client generates the id, as a UUID.** The phone has to know the id before the first attempt, and a random UUID makes collisions between entries impossible in practice. Validated with zod's `z.uuid()`, then lower-cased before storing or looking up, so `ABC…` and `abc…` are the same entry.
   - *Alternative:* an `Idempotency-Key` header with a separate table of keys and cached responses. More general, but it needs storage and expiry for something that is really a property of the entry. A column on the entry is simpler and also lets the app match its queued entries with the stored ones (see 4).

2. **Storage: a nullable `client_id` text column with a unique index**, on `meals` and `water_logs`. SQLite allows any number of `NULL`s under a unique index, so existing rows and requests without `clientId` are unaffected. The migration is generated with `drizzle-kit generate` (`ALTER TABLE … ADD client_id`, `CREATE UNIQUE INDEX`), and needs no backfill.

3. **Replay = look up, then insert, in one transaction.** In the repository: if `clientId` is given, look for an entry with it and return it marked as existing; otherwise insert. For meals the meal and its items are inserted in the same transaction, which also fixes the current non-atomic insert. Because the process is single-threaded and the callback is synchronous, the lookup and insert can't interleave with another request. The unique index is the backstop: if it ever rejects an insert, that's a bug, not a normal path, and it surfaces as a 500.
   - The repository returns `{ entry, created: boolean }` and the route answers **201** when `created`, **200** otherwise. Same body shape either way, so the client only has to treat any 2xx as "sent".
   - *Alternative:* `INSERT … ON CONFLICT DO NOTHING` and then select. It works for water, but for meals the items insert depends on the new id, so it needs the same branching anyway.

4. **Responses include `clientId`** (`string | null`) on meal entries (`toMealEntry` and `MealEntry`) and water entries (already the raw row). The app's cache (#69, #70) can then replace a pending local entry with the stored one by matching ids. The CSV export and summaries don't change.

5. **A replay ignores the repeated body**, including its `occurredAt`/`loggedAt`. The request is still validated first, so a malformed retry gets 400 like any other request; a well-formed one returns the stored entry unchanged.

6. **Deleting an entry frees its `clientId`.** After a delete, a later request with the same id creates a new entry. Offline deletes are out of scope (#70), so a queued retry can't race a delete in practice.

## Risks / Trade-offs

- **A different entry reusing a `clientId`** would be silently dropped and answered with the old entry. → UUIDs generated per entry make that a client bug; the spec states the id is generated once per entry.
- **Migration on existing databases** (PC and laptop). → Additive (nullable column plus index), no backfill; tested by opening a database at the previous migration, adding data, then applying the new migration.
- **Larger responses** by one field. → Negligible; the app ignores unknown keys.
- **The laptop backend runs an older copy** until it is redeployed. → Only matters once the app sends `clientId` (#70); an old backend ignores the unknown field, so it degrades to today's behaviour rather than failing.

# Design

## Context

- `DayContent` (`ui/home/DayContent.kt`) is the single screen body behind Home (today) and the History day detail (`DayDetailScreen`). On every `(date, reloadKey)` change it calls `listMeals`, `getGoals` and `getWater` in sequence, keeps them in `remember` state, dims the previous content while loading, and shows only an error when any call fails. Actions (favorite, delete) bump `reloadKey`; water actions refetch only the water.
- There is no persistence for API data. Settings are JSON in SharedPreferences (`PreferencesStore`), loaded and saved by `MainActivity`, which also pushes the server address and token into `BackendConfig` when Options change.
- `createHttpClient` installs only content negotiation and the auth header. The Android engine's default connect timeout is long (around 100 s), so an unreachable backend currently shows a spinner for that long.
- `ApiException(message, status)` is thrown when the backend answered with an error. Any other exception from a call means the request didn't get an answer (no network, DNS, refused, timeout).
- The backup rules (`backup_rules.xml`, `data_extraction_rules.xml`) already exclude the `root`, `file`, `database`, `sharedpref` and `external` domains, and the manifest sets `allowBackup="false"`.
- Tests run as `testDebugUnitTest` on the JVM: `commonTest` (with Ktor's `MockEngine`) and `androidUnitTest`. There is no Robolectric and no instrumented test setup, so Android `Context` isn't available in unit tests.
- The project declares iOS targets but there is no Xcode project; Kotlin/Native targets are disabled on this Linux machine and CI only builds Android.

## Goals / Non-Goals

**Goals:**
- Home and the day detail render the last known day instantly and stay usable read-only without a connection.
- A clear, localized signal when what's on screen may be stale, and a quick one (≤ 10 s) when the backend is unreachable.
- A local database that #70 and #71 can extend with their own tables through Room migrations.

**Non-Goals:**
- Caching Summary, charts, History's month calendar and list, favorites in Capture, Goals, or the CSV export.
- Any write without a connection (#70).
- Syncing or merging: the cache is a copy of what the backend last returned, never a source of truth.
- Building or verifying the iOS app.

## Decisions

1. **Room 3 (`androidx.room3`) 3.0.3 with `androidx.sqlite:sqlite-bundled` 2.7.1 and KSP 2.3.12**, configured in `commonMain`. The database class is annotated `@ConstructedBy` with an `expect object` constructor generated by KSP per target; KSP runs for the Android and the iOS targets. Room 3 doesn't publish `iosX64` (Intel simulators, deprecated by Kotlin), so that target is removed from the build. `setQueryCoroutineContext(Dispatchers.IO)` and `BundledSQLiteDriver` are set in the builder. The Room 3 Gradle plugin exports the schema to `composeApp/schemas/`, committed, so later migrations (#70) can be checked against it.
   - *Why Room 3 and not Room 2.8 KMP:* Room 3 is the Kotlin-first line where multiplatform is the default; a new database has no migration cost. *Fallback:* if Room 3 or KSP 2.3.12 doesn't build with Kotlin 2.4.20 and AGP 8.13.2 (task 1.1 checks this before anything else), use Room 2.8.x (`androidx.room`), whose KMP API is nearly the same, and record it here.
   - *Why bundled SQLite:* the same SQLite on every platform and in JVM tests.

2. **Snapshot tables holding the API's JSON**, version 1:
   - `day_cache(date TEXT PRIMARY KEY, meals_json TEXT, water_json TEXT, server_url TEXT, refreshed_at INTEGER)`: the `List<MealEntry>` and `WaterDay` exactly as received, re-encoded with the app's `Json`;
   - `goal_cache(id INTEGER PRIMARY KEY, goal_json TEXT, server_url TEXT, refreshed_at INTEGER)`, always written with `id = 1`.

   The cache is only a display copy of three responses, so storing them as JSON keeps one model (the API's) and needs no schema change when the API adds a field. A row that no longer decodes is treated as missing and deleted. *Alternative:* normalized meal/item/water tables. They'd duplicate the API model and need migrations for every API field, with no query that needs them yet; #70's pending entries live in their own table anyway.

3. **`DayRepository` in `commonMain`** between the UI and the API:
   - `observe(date): Flow<CachedDay?>`, where `CachedDay` holds the meals, the water, the goal and the oldest `refreshedAt` of its parts; `null` when the day or the goal isn't cached;
   - `suspend refresh(date): RefreshResult`, which fetches the three responses, then writes the day and the goal in one transaction and returns `Success`, `Offline` (the request got no answer) or `Failed(exception)` (the backend answered with an error);
   - `suspend clear()`.

   The repository talks to the database through a small `DayCacheStore` interface implemented by the Room DAO. `commonTest` tests the repository with an in-memory fake store and `MockEngine`; the DAO and the database are exercised on the emulator, since unit tests have no Android `Context`.

4. **Classifying failures:** `ApiException` means the backend answered → `Failed`, and its message goes through the existing `errorText` (so 401 keeps its localized text). Any other exception except `CancellationException` → `Offline`.

5. **`DayContent` reads from the repository.** It collects `observe(date)` and calls `refresh(date)` on `(date, reloadKey)` changes, as now. Rendering:
   - cached day present → show it, no dimming;
   - no cached day and a refresh in flight → current behaviour (dim the previous day, or the first-load indicator);
   - refresh `Offline` → a one-line notice above the content: "Sin conexión · datos de las 14:32" / "No connection · data from 14:32", with the date when the copy isn't from today;
   - refresh `Failed` → the error text above the cached content; without a cached day, the error alone, as today.

   Water actions keep their own refetch, which now goes through `refresh` so the cache gets the new water too. A `LifecycleResumeEffect` bumps `reloadKey` on resume, skipping the first resume so opening the screen doesn't refresh twice.

6. **Connection timeout:** `createHttpClient` installs `HttpTimeout` with `connectTimeoutMillis = 10_000` only. Request and socket timeouts stay unlimited, because an analysis can take long once connected. The Options connection test keeps its own shorter client.

7. **Server change clears the cache, without races:** `MainActivity.onPreferencesChange` compares the effective server URL before and after; when it changes, it calls `clear()`. A refresh started against the old server could still land afterwards, so each written row carries `server_url`, and `observe` only returns rows whose `server_url` equals the current `BackendConfig.baseUrl`. A refresh also drops its result if the URL changed while it ran.

8. **One database per process**, built lazily in `androidMain` from the application context (`food-tracker-cache.db` in the app's databases directory) and passed to `App` as a `DayRepository`. `App` keeps a default parameter so previews and the iOS entry point compile; the iOS builder uses the app's documents directory, unverified here.

9. **Backups:** no rule change. The database file lives in the `database` domain, which both rule files already exclude; verified with `adb shell bmgr` on the emulator.

## Risks / Trade-offs

- **Room 3 / KSP compatibility with Kotlin 2.4.20 and AGP 8.13.2** → checked in task 1.1 before writing the feature; fallback in D1.
- **APK size**: the bundled SQLite adds a native library per ABI. The debug APK grows from 17.4 MB to 22.6 MB (measured in task 1.1). Acceptable for a personal app; ABI splits could cut it later.
- **Build time**: KSP adds a processing step to every build. Acceptable.
- **A cached day hides deletions made elsewhere** until the refresh arrives (≤ 10 s offline detection, usually under a second at home). The notice makes stale data visible when the refresh fails.
- **Unbounded cache growth**: one small row per visited day (a few KB). Not pruned; can be added later if it ever matters.
- **iOS code can't be compiled here** → kept minimal (builder plus KSP configuration) and called out in the PR.
